# PromoGuard — STRIDE Threat Model

Generated by the `stride-threat-model` skill against `app/agent.py` and `app/security.py`.

## System Boundaries
- **Entry points**: `ingest` node (Pub/Sub or local JSON event), `redeem_promotion` tool,
  `review_agent` (Gemini), `human_review` (RequestInput).
- **Data stores**: `PROMO_STORE` (promotion ledger), `LOYALTY_LEDGER` (audit log).
- **Trust boundary**: every event crossing `ingest` is untrusted until validated by the
  `RedemptionRequest` Pydantic schema and the `security_check` node.

## STRIDE Assessment

| Pillar | Threat | Mitigation in PromoGuard | Residual risk |
|--------|--------|--------------------------|---------------|
| **Spoofing** | Guest/anonymous user redeems member-only promo | `redeem_promotion` rejects empty/`guest_` IDs (Elevation guard) | Member-ID spoofing if upstream auth is weak — enforce SSO at gateway |
| **Tampering** | Caller inflates `value` or replays a code | Code value is read from server-side `PROMO_STORE`, not the request; single-use set per member | Needs DB-level optimistic locking in prod (race condition) |
| **Repudiation** | Member denies redeeming | Every redemption + decision appended to `LOYALTY_LEDGER` with timestamp | Ledger is in-memory in the lab; back with append-only store in prod |
| **Information Disclosure** | Card/TFN/email in free-text reaches LLM or logs | `redact_pii` scrubs before model + logs; categories recorded | Pair with managed DLP for broader coverage |
| **Denial of Service** | Code-farming / LLM cost abuse | Velocity limit (3/min) + deterministic routing keeps LLM off the low-value path | Add per-store and global rate limits |
| **Elevation of Privilege** | Prompt injection forces auto-approval | `detect_prompt_injection` short-circuits to human review; LLM never executes redemptions | Keep injection signal list current |

## Priority Recommendations
1. Replace in-memory stores with a transactional DB using pessimistic locking
   (`.with_for_update()`) to close the double-redemption race window.
2. Enforce loyalty-member authentication at the API gateway (mTLS / OIDC) before events
   reach `ingest`.
3. Ship `LOYALTY_LEDGER` to an append-only, tamper-evident audit sink.
